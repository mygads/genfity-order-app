# Audit RBAC Terminal Genfity Order — Model Target vs Kondisi Kini (App)

> READ-ONLY. Tidak ada perubahan file. Semua klaim faktual mempertahankan bukti `file:line` dari hasil verifikasi adversarial. Nama kode/endpoint dalam Bahasa Inggris, narasi Bahasa Indonesia.

---

## 1. Ringkasan Eksekutif

- **Kesenjangan keseluruhan besar**: fondasi yang sudah benar adalah sesi owner/staff, klaim terminal per-device, settings server-wins, offline-first + auto-sync, dan varian struk kasir vs dapur — tetapi **seluruh alur login terminal model target (RBAC BE → pilih branch → pilih terminal → PIN terminal) belum ada**.
- **Kosakata 4 tag (`kasir`, `dapur`, `view_pelanggan`, `view_queue`) + konsep untagged=full-access tidak ada di mana pun**: kode hanya mengenal `KASIR|DAPUR|DISPLAY`, kontrak hanya mengenal `deviceRole KASIR|DAPUR|DISPLAY`, tidak ada `view_queue`, tidak ada pairing 1:1, tidak ada SSE.
- **3 blocker teratas**: (1) Tidak ada RBAC BE "bolehkah user ini akses terminal" saat login — login local-first SQLite sehingga validasi BE dapat di-bypass (`auth-01`, `termreg-login-flow`, `contract-login-flow`); (2) Tidak ada terminal picker + PIN terminal + CRUD terminal owner (`auth-02`, `auth-03`, `termreg-no-crud`, `contract-terminal-crud`, `contract-terminal-pin`); (3) Tidak ada transport SSE padahal `view_pelanggan`/`view_queue` wajib online-only SSE, dan tidak ada routing event per-tag (`termreg-no-sse`, `realtime-01`, `realtime-02`, `contract-event-subscription`).
- **Risiko data offline terbesar**: dua terminal offline bersamaan akan mencetak nomor `TRX-YYYYMMDD-NNN` identik (PK `salesNum`) sehingga merge diam-diam hilang via `INSERT OR IGNORE`, dan tidak ada resolusi konflik untuk edit konkuren pada bill yang sama (`offline-salesnum-collision-two-devices`, `offline-no-conflict-resolution`).
- **Risiko printer terbesar**: pairing printer bersifat global per-device tanpa scoping `branchId`/`terminalCode`, sehingga printer branch A terbawa ke sesi branch B; 1-device:1-printer tidak dapat diekspresikan/dipaksakan (`printer-branch-scoping-absent`, `printer-one-to-one-not-enforced`).
- **Kontrak BE-dokumen vs kode saling bertentangan** pada dua titik (`terminal/update` dan `terminal/get-terminal`), dan seluruh CRUD staff/terminal/branch-list, terminal-PIN, pairing 1:1, dan langganan event per-tag belum ada di kontrak (`contract-terminal-update-shape`, `contract-get-terminal-shape`, `contract-staff-crud`, `contract-view-pairing`).
- **Arah perbaikan**: Fase 1 fondasi sesi+RBAC dan kontrak, Fase 2 picker+PIN+tag lock, Fase 3 routing event+printer 1:1, Fase 4 SSE display-only + partisi multi-branch. Setiap fase punya acceptance criteria di §5.
- **Keputusan produk yang menahan implementasi**: definisi full-access (untagged?), flow PIN via QR, siapa boleh unpair `view_pelanggan`, dan shift-gate untuk display-only — dirinci di §6.

## 3. Temuan per Dimensi

### 3.1 Auth

**Sudah sesuai (tidak perlu tindakan):**

- **A-OK1 — Role Owner vs Staff dimodelkan dan tersimpan di sesi, dengan normalisasi kanonis.** Bukti: `src/session.ts:7-13`; `src/session.ts:88-99`; `src/lib/access.ts:30-33`; `src/lib/access.ts:40-61`.
- **A-OK2 — Jalur login username+password (PIN) staff ada dengan kontrak validasi employee yang terdefinisi.** Bukti: `src/screens/auth/LoginScreen.tsx:161-208`; `src/lib/apiSource.ts:539-590`; `src/lib/apiSource.ts:461-468`.
- **A-OK3 — Identitas terminal yang diklaim (terminalCode+branchId) persisten dan terpasang di trafik API.** Bukti: `src/screens/install/InstallScreen.tsx:32`; `src/config/server.ts:239-247`; `src/config/server.ts:267-298`.
- **A-OK4 — Layar branch-picker ada (saat ini install-time) sehingga dapat dipakai ulang oleh flow login.** Bukti: `src/screens/install/SelectBranchScreen.tsx:7-29`.
- **A-OK5 — Disiplin hashing PIN: plaintext hanya di memori, hash di SecureStore dengan fallback AsyncStorage.** Bukti: `src/lib/pin.ts:175-196`; `src/screens/auth/LoginScreen.tsx:136-144`.
- **A-OK6 — Supervisor approval melengkapi (bukan menggantikan) model owner/staff sebagai gerbang eskalasi, dan fail-closed saat offline.** Bukti: `src/lib/supervisor.ts:2-10`; `src/lib/supervisor.ts:82-110`; `src/lib/supervisor.ts:130-143`.

**Temuan:**

- **[auth-01] (blocker) — Tidak ada pemeriksaan RBAC BE "bolehkah user ini akses terminal" saat login; login bersifat local-first SQLite dan tidak pernah mengotorisasi user terhadap terminal/branch yang diklaim.** Persyaratan: langkah 1 flow login terminal model target. Bukti: `src/lib/apiSource.ts:539-549`; `src/lib/apiSource.ts:560-562` (body server hanya {username, pin}); `src/screens/auth/LoginScreen.tsx:180`; `src/config/server.ts:39-132` (tanpa endpoint terminal-access/RBAC). Saran: tambah endpoint BE (mis. `terminal/check-access {userId, terminalCode}`) yang dipanggil setelah `validateEmployee`/`loginByQrCode` sebelum sesi dibuat; fail-closed saat ditolak atau offline tanpa grant sebelumnya.
- **[auth-02] (blocker) — Tidak ada layar terminal picker; device terikat ke satu terminal pra-klaim saat install, bukan dipilih per login.** Persyaratan: langkah 3 flow login. Bukti: `src/navigation/types.ts:14-81`; `src/screens/install/InstallScreen.tsx:32`; `src/screens/auth/LoginScreen.tsx:161-208`. Saran: tambah layar TerminalPicker yang dipanggil dari login (setelah resolusi branch), berisi daftar terminal BE untuk branch tersebut; simpan terminalCode terpilih di sesi per login, bukan hanya saat install.
- **[auth-03] (blocker) — Tidak ada entri PIN terminal saat login yang divalidasi ke PIN per-terminal BE; satu-satunya layar PIN adalah pembuatan install-time dan kredensial username.** Persyaratan: langkah 4 flow login (QR TBD). Bukti: `src/screens/auth/LoginScreen.tsx:384-461`; `src/screens/install/CreatePinScreen.tsx:24-25`; `src/screens/auth/LoginScreen.tsx:136-151`. Saran: tambah langkah terminal-PIN setelah seleksi terminal yang diverifikasi ke BE (PIN per-terminal), berbeda dari kredensial user; pertahankan QR-PIN sebagai placeholder TBD eksplisit.
- **[auth-04] (blocker) — Staff-ke-multi-branch tidak didukung struktural: satu kolom branchId TEXT per user, tanpa tabel pemetaan, dan sesi tanpa daftar branch.** Persyaratan: satu staff boleh milik banyak branch; >1 branch memicu branch picker. Bukti: `src/lib/dbSchema.ts:14-16`; `src/lib/master.ts:79-85`; `src/session.ts:7-18`; `src/session.ts:26-34` (outlet DEMO hardcoded). Saran: tambah pemetaan user-branch (tabel + domain pull) atau klaim multi-branch di payload user; perluas sesi dengan branchId aktif + daftar branch aksesibel; gerakkan branch picker login dari data itu.
- **[auth-05] (major) — SelectBranchScreen hanya install-time dan tidak tersambung ke login; user multi-branch tidak mendapat pilihan branch saat sign-in.** Persyaratan: branch picker muncul selama login terminal bila >1 branch. Bukti: `App.tsx:236-246`; `src/screens/install/SelectBranchScreen.tsx:27`; `src/screens/auth/LoginScreen.tsx:161-208`. Saran: pakai ulang SelectBranchScreen (atau varian login) di dalam flow login dengan umpan daftar branch aksesibel user.
- **[auth-06] (major) — Sesi membuang konteks login: authKey dan branchId dari EmployeeSession dibuang dan outlet tidak pernah diperbarui dari login/terminal.** Persyaratan: sesi mencerminkan siapa login, ke branch/terminal mana. Bukti: `src/lib/apiSource.ts:461-468`; `src/screens/auth/LoginScreen.tsx:145`; `src/session.ts:88-99`. Saran: persistensikan branchId aktif, terminalCode, dan authKey/token di sesi saat login; set tampilan outlet/branch dari branch yang teresolusi, bukan default DEMO.
- **[auth-07] (major) — Login offline berhasil hanya dengan hash SQLite lokal, sehingga validasi BE dapat di-bypass by design (local-first dengan fallback dummy/lokal).** Persyaratan: login memvalidasi ke BE dengan RBAC terminal; mode offline dicadangkan untuk auto-sync kasir/dapur/full-access, bukan entri tanpa autentikasi. Bukti: `src/lib/apiSource.ts:490-528`; `src/lib/apiSource.ts:229-234`; `src/screens/auth/LoginScreen.tsx:164-180`. Saran: definisikan dan tegakkan kebijakan offline-login (mis. hanya pasangan user+terminal yang pernah diotorisasi BE boleh masuk offline lagi, dengan expiry), bukan semua user seed lokal yang login selamanya.
- **[auth-08] (major) — Daftar branch hardcoded dengan timer loading palsu, bukan data BE per-user, sehingga login tidak pernah bisa menawarkan branch yang benar.** Persyaratan: branch picker mencerminkan branch yang boleh diakses user menurut BE. Bukti: `src/screens/install/SelectBranchScreen.tsx:4-7`; `src/screens/install/SelectBranchScreen.tsx:15-18` (setTimeout 900ms); `src/screens/install/SelectBranchScreen.tsx:27`. Saran: ganti daftar hardcoded dengan branch aksesibel dari BE untuk user terautentikasi; pertahankan entri statis hanya sebagai fallback offline.
- **[auth-10] (minor) — Login QR ada tetapi menarget flow host ESB legacy, sementara flow PIN-terminal via QR model target masih TBD; keduanya mudah tertukar.** Persyaratan: entri PIN terminal saat login; flow PIN via QR TBD/open. Bukti: `src/lib/apiSource.ts:592-616`; `src/lib/apiSource.ts:625-647`; `src/screens/auth/QrHowScreen.tsx:60-64`. Saran: labeli login QR eksisting sebagai legacy/paritas-ESB dan cadangkan langkah terminal-PIN (QR) terpisah; jangan tampilkan login QR kini sebagai solusi PIN-terminal.
- **[auth-11] (major) — Login buta-tag: tidak ada konsep tag terminal (kasir/dapur/view_pelanggan/view_queue) atau untagged-full-access yang mencapai auth/sesi.** Persyaratan: tepat 4 tag owner; untagged=full access; halaman view terkunci. Bukti: `src/lib/deviceRole.ts:15`; `src/lib/terminal.ts:25`; `src/session.ts:7-18`. Saran: tarik tag terminal BE saat login/klaim ke dalam sesi dan pemetaan peran device (termasuk untagged full-access dan dua mode view terkunci) sebelum menegakkan kunci navigasi.
- **[auth-12] (major) — RBAC dalam-app default-allow saat baris aturan tidak ada, sehingga aturan terminal-access yang hilang akan diam-diam memberi akses, bukan menolak.** Persyaratan: RBAC BE menolak akses terminal kecuali diizinkan eksplisit. Bukti: `src/lib/access.ts:150-153`; `src/lib/access.ts:159-166`; `src/lib/access.ts:172-182`. Saran: pertahankan fail-open hanya untuk empat kunci aksi dalam-app bila produk mewajibkan, tetapi buat gerbang terminal-access di masa depan fail-closed (tolak pada user/terminal tak dikenal atau DB-unready).

## 7. Revisi model hasil klarifikasi — okupansi tunggal, claim/kick, dua PIN (2026-10-17)

### 7.1 Aturan sesi: 1 terminal : 1 user : 1 device

- Satu terminal dalam satu waktu hanya dipegang **satu user di satu device** (okupansi tunggal — anti tabrakan).
- Satu user **boleh** memegang sesi di N terminal/N device bersamaan (contoh: 3 terminal di 3 device OK).
- Satu device terikat tepat **satu terminal** dalam satu waktu (binding persist; ganti terminal = re-bind).
- **Claim/kick**: login baru yang sukses di terminal yang sedang terisi → sesi lama di-KICK (logout paksa di device lama + notifikasi + audit log). Dua pemicu: (a) user berbeda login di device yang sama; (b) device lain me-re-bind terminal itu (wajib PIN terminal + otorisasi, lihat Q14).
- **Logout** = akhiri sesi user saja; binding device↔terminal tetap. Login screen wajib menampilkan identitas binding: "Selamat datang di {merchant} — {terminal}".
- **Rekonsiliasi picker**: pilihan branch → terminal → PIN terminal terjadi di **bind-time** (fresh device / re-bind), BUKAN di setiap login. Device yang sudah ter-bound langsung ke login (akun + password + PIN staff), tanpa picker.

### 7.2 Dua PIN yang berbeda + matriks pemakaian

| PIN | Lingkup, diset oleh | Dipakai untuk |
|---|---|---|
| PIN terminal | Per terminal, owner | Bind device baru (dan re-bind). SEKALI per device, BUKAN per login |
| PIN staff (pin kasir) | Per akun staff, pengaturan di BE | Login (bersama username+password), absensi, buka shift, tutup shift |
| PIN owner | Per akun owner | Superset: semua fungsi PIN staff + approval **void / cancel / kompliment**; setiap pemakaian tercatat (audit trail, "terekap sama kayak staff") |

- Alur fresh device: [pilih branch →] pilih terminal → PIN terminal (bind) → login (username+password+PIN staff).
- Alur device ter-bound: langsung login.
- Pemetaan ke kode eksisting: `verifyAttendancePin` (`src/lib/pin.ts`, dipakai `src/lib/supervisor.ts:15`; hashing A-OK5) = benih PIN staff; `authorizeSupervisor` → `ApiPath.supervisorApprove` (`src/lib/supervisor.ts:113-145`) = benih approval PIN owner untuk void/kompliment; `CreatePinScreen` install-time = legacy, jangan dicampur dengan PIN terminal.

### 9.2 Q7 RECOMMENDED — identitas sale offline hibrida (disarankan, menunggu konfirmasi)

- **PK + idempotensi: UUIDv7** dibuat di device (`client_id`). Unik global tanpa koordinasi server, terurut waktu (baik untuk indeks SQLite), aman untuk retry/outbox lintas device.
- **Nomor display: tersegmen** `TRX-{branch}-{terminal}-{YYYYMMDD}-{NNN}` (contoh `TRX-B001-K01-20261017-0042`, 26 char muat di struk 58mm). Dibuat lokal saat offline, **FINAL** — tidak berubah pasca-sync sehingga struk yang sudah di-print tetap valid. `NNN` = counter per (terminal, tanggal) yang persist di device.
- **Server**: `UNIQUE(display_no)` sebagai backstop; konflik → 409 eksplisit yang tampil ke kasir, **bukan** `INSERT OR IGNORE` diam-diam. Upsert push berdasarkan `client_id` (retry aman).
- Mengapa bukan murni salah satu: UUID murni tak ramah manusia (tak bisa dibaca via telepon, jelek di struk); sequence murni server-side mematikan mode offline; counter per-device tanpa segmen = tabrakan hari ini.
- Langkah migrasi: (1) tambah kolom `client_id` + backfill untuk baris lama, jadikan identitas merge; (2) `salesNum` jadi display-only format tersegmen; (3) generator UUIDv7 tanpa dep (~15 baris, timestamp+`expo-crypto` random); counter per (terminalCode dari binding §7, tanggal) dengan init dari MAX lokal; (4) device belum ter-bound **dilarang** membuat sale (tutup `termreg-branch-fallback`); (5) push bawa `(client_id, display_no, branchId, terminalCode)`; (6) UUID yang sama untuk outbox/expense/doc-id (`offline-ids-not-globally-unique`, `offline-expense-id-short`); (7) baris lama tidak ditulis ulang — format baru hanya untuk sale baru.

## 12. Penguncian Q6 + Q7 — model 100% terkunci untuk Fase 1–3 (2026-10-17)

### 12.1 Q7 CLOSED — hibrida UUIDv7 + tersegmen (nilai final)

- **PK/merge/idempotensi**: `client_id` **UUIDv7** device-generated (48-bit timestamp + random via `expo-crypto`, ~15 baris tanpa dep). Satu generator untuk sale, outbox, expense, doc-id.
- **Nomor display**: `TRX-{BRANCH}-{TERM}-{YYYYMMDD}-{NNNN}` — `NNNN` 4-digit zero-padded (0001–9999/hari/terminal, lanjut 5 digit bila jebol); contoh `TRX-B001-K01-20261017-0042` (26 char, muat struk 58mm).
- **Syarat BE**: `terminalCode` unik per branch, ≤8 char alfanumerik kapital (dikunci di validasi create-terminal); PK tabel = uuid; `UNIQUE(display_no)`; push upsert by `client_id`; konflik display_no → **409 terlihat**, bukan silent-ignore.
- **Counter** per `(terminalCode, tanggal)` persist di SQLite, init dari `MAX(suffix)` lokal; device belum ter-bound **dilarang** membuat sale.
- **QR pembayaran** membawa `client_id` (stabil), bukan nomor display (menutup `realtime-10`).
- **Migrasi aditif**: tambah kolom + backfill; baris lama tidak ditulis ulang; BE terima dua format selama transisi.

### 12.2 Q6 CLOSED — grant offline 7 hari sliding, server-driven (nilai final)

- **TTL 7 hari** sejak otorisasi BE terakhir, **sliding** (auth online sukses memperpanjang); **login pertama wajib online**; PIN staff tetap wajib dimasukkan tiap login offline (vs hash cache).
- Grant terikat `(user, terminal, device)`; revoke/unbind/ganti-role ditegakkan saat online pertama; kick "baru menang" menutup sesi zombie.
- **Trade-off diterima**: ganti PIN owner/staff maks 7 hari masih bisa dipakai di device offline (harga mode offline).
- **Policy key** `max_offline_grant_days` (default 7) via `pull-terminal-settings` (server-wins) — BE bisa mengecilkan untuk merchant high-risk tanpa update APK. Selaras dengan blokir sync 7-hari: satu angka, satu pintu.
- Masuk Fase 1 (grant-cache + fail-closed + endpoint `staff-login`).
